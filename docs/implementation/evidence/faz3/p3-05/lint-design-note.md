## Aile 1 — `AndroidDeviceCheck.kt:40` (`canAuthenticate`) ve `:45` (`BiometricPrompt.authenticate`)
- **İspat, erişilebilirlik/guard:** `prompt()` yalnız `Build.VERSION.SDK_INT >= R` (30) dalından çağrılır (`:24`), ayrıca `@TargetApi(R)`; altı API'ler çağırıcıya yalnız API≥30'da ulaşır. API<30'da mevcut yol Keyguard `createConfirmDeviceCredentialIntent` (ADR0029 satır 74–79: "BiometricPrompt BIOMETRIC_STRONG|DEVICE_CREDENTIAL on API 30+, otherwise the Keyguard credential screen"; kilit yoksa `recovery_lock_required`). Biyometrik onay mantığı/yetkilendirme kümesi (`BIOMETRIC_STRONG|DEVICE_CREDENTIAL`) lint düzeltmesinin konusu değil.
- **İspat, izin durumu:** Modül manifesti (`modules/my-module/android/src/main/AndroidManifest.xml`) `USE_BIOMETRIC` bildirmiyor; uygulama `AndroidManifest.xml` de bildirmiyor (CAMERA, INTERNET, READ_MEDIA_*, SYSTEM_ALERT_WINDOW, VIBRATE, depolama). **Birleşik debug manifestte** (P3-02 klonu `merged_manifest/debug/processDebugMainManifest`) `USE_BIOMETRIC` ve `USE_FINGERPRINT` **var**; merger raporu kaynağı `androidx.biometric:biometric:1.1.0` kütüphane manifesti (`transformed/biometric-1.1.0/AndroidManifest.xml:24`). Yani çalışma zamanı izni dolaylı bağımlılıktan gelir; modül lint'i yalnız kendi manifestine baktığı için "Missing permissions" üretir. Kod bu izne doğrudan dayanıyor ama kaynağı kendi bildirmiyor (kırılgan: bağımlılık kalkarsa çalışma zamanı `SecurityException`, lint'in uyardığı durum).
- **Önerilen en küçük düzeltme (davranış/izin kapsamı değişmez):** `modules/my-module/android/src/main/AndroidManifest.xml`'e `<uses-permission android:name="android.permission.USE_BIOMETRIC" />` eklemek. Birleşik manifestte aynı izin zaten var → nihai APK izin kümesi aynı (tek satır birleşir); `USE_FINGERPRINT` eklenmez. Lint suppression yok.
- **Doğrulanmamış:** düzeltmenin lint hatalarını gerçekten kapattığı koşulmadı (yasak). Beklenen: `:my-module:lintDebug` `MissingPermission` 2→0.
- **Kullanıcı kararı gerekir mi?** Hayır, mevcut ADR0029/izin durumu içinde; yalnız bildirimin modül düzeyine taşınması. (Karar gerekirse: kullanıcı "izinleri yalnız uygulama manifestinde tut" derse alternatif `apps/mobile` app manifestine ekleme; birleşik sonuç aynı.)
- **Sonraki en küçük test:** düzeltme sonrası (a) P3-02 aynı bayraklarla merged manifest izin listesi öncesi/sonrası `diff` (beklenen fark 0) ve (b) `:my-module:lintDebug` dar koşu `MissingPermission` sayısı. İzinli dosya: yalnız `modules/my-module/android/src/main/AndroidManifest.xml`.

## Aile 2 — `AndroidS3Automatic.kt:46` `JobInfo.Builder.setRequiresBatteryNotLow(true)` (API 26, min 24)
- **İspat, erişilebilirlik:** `minSdkVersion 24` (`modules/my-module/android/build.gradle:26`). Setter yalnız `AndroidS3JobOs.schedule` içinde, çağıran `AndroidS3AutomaticCoordinator.kt:199` (`catch (_: Exception)`). Çağıran zinciri: `AndroidS3Automatic.coordinator/reconcile` ← `KlodaS3Module` OnCreate/foreground, `enableS3/disableS3/pauseS3`, `AndroidBackupReceiver:17`, `AndroidBackupScheduler:72,83` — **hiçbirinde SDK guard yok**; S3 çalışma zamanı `AndroidS3Runtime` da API kapısı içermiyor (SMB/SFTP `supported()` API≥33 gate'i, S3'te yok). Bu nedenle API 24/25 cihazda `NoSuchMethodError` (bir `Error`; `catch Exception` yakalamaz) kaynak düzeyinde beklenir — **cihazda doğrulanmadı** (API 24/25 emülatör kanıtı yok; S3 otomatik testleri API35).
- **Kıyas:** diğer tüm otomatik işler (WebDAV/SMB/SFTP/FTPS/backup) battery-not-low kullanmıyor; yalnız S3 `UNMETERED + BatteryNotLow + persisted` ister. Batarya kısıtı için ADR/doküman kararı bulunamadı (`docs/decisions` içinde yok) → kısıt bilinçli bir S3 politikası, ADR dayanağı yok.
- **Alternatifler (hepsi API 24/25 davranışını değiştirir):** (1) `SDK_INT>=26` ise kısıtı ekle, altında ekleme → API 24/25'te **düşük pil kısıtı sessizce kalkar** (talimatla yasak sınır); (2) S3 otomatik zamanlamayı API<26'da desteklenmez yap (SMB/SFTP gate örneği gibi; kısıt korunur, özellik API 24/25'te kapanır, kullanıcıya görünür durum gerekir); (3) API<26'da iş başında pil seviyesini ayrıca kontrol et (yeni yürütme davranışı/testi).
- **Kullanıcıdan istenecek tek karar:** "S3 otomatik yedekleme Android 7.x'te (API 24/25) nasıl davransın: (A) bu sürümlerde desteklenmesin/kapalı kalsın (pil kısıtı korunur), (B) pil kısıtı olmadan çalışsın, yoksa (C) pil kontrolü iş başında yapılsın?" Öneri: A (kısıt ve güvenlik korunur, en dar, mevcut SMB/SFTP gate kalıbı). Karar gelmeden kaynak değişmez.
- **Sonraki en küçük test (karar sonrası):** host/JVM seviyesinde S3 zamanlama sözleşmesi için API<26/≥26 dalı birim kontrolü (mevcut `S3RecordingOs` test harness'i ile), sonra dar `:my-module:lintDebug` `NewApi` 1→0. İzinli dosya adayları: `AndroidS3Automatic.kt` (A/B/C'ye göre) ve gerekirse `KlodaS3Module.kt` durum alanı + mevcut S3 test dosyası.
