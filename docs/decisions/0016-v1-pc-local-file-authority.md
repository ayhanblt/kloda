# ADR0016 — V1 PC-local file authority

2026-10-19 scoped owner-management addition: [ADR0019](0019-desktop-device-removal-and-recoverable-backup-deletion.md) approves PC-local offline trust+ACL device removal and future local recoverable backup deletion. This does not add delete to remote/default ACL; original phone online/offline unpair semantics remain unchanged.

- Date: 2026-10-13 (documentation date, not an inferred approval timestamp).
- Owner: Ayhan.
- Status: **APPROVED V1 direction; native file receiver, durable journal and online unpair are implemented; production and physical acceptance remain open**.
- Scope: PC-local backup-scope approval and LAN file authorization. Scoped supersession of ADR0003–0014 only where they mandate central issuance, account eligibility/step-up, exact-DER online reissue or a `<24h` central cache for this local ACL. Historical decisions/evidence remain preserved. ADR0015 platform/signing isolation is unchanged.

## Decision

1. **Native Rust is the sole file authority.** Native owns a durable SQLite ACL in local application data, its transactions, admission, current authorization and revoke/publication fence. Electron is management UI only: it requests PC selections/approval and displays native results; renderer/main flags, writable caller authority contexts or a managed path check cannot grant access.
2. **QR trust and file approval are separate.** The frozen [KLODA-QR-PAIR-V1 protocol](../security/qr-pairing-v1-protocol.md) is unchanged. Explicit PC approval of a QR candidate establishes peer trust, not a file grant. A user must separately select a PC backup folder/scope and explicitly approve that peer's file access. **No selected folder means pairing only**, with no file operations.
3. V1 default scope permits **photo upload, status, finalize, listing that peer's OWN backup, and user-triggered restore of its own backup**. The subsequent user-requested mobile sender also permits selected Files one-way backup through these same upload/status/finalize/own-list/own-download operations and existing PC-local consent; it does not create a broader API or grant. Delete, another peer's backup, outside-root access, bidirectional sync, arbitrary PC browsing and conflict/retention behavior remain excluded. Existing broader product intentions are not automatically ACL permissions.
4. A **new local grant and LAN operation require no central backend, login, account JWT, central signed capability/issuer, KMS or 24-hour central-check cache**. QR trust alone still cannot create the grant. Native must verify the current local ACL and the current operation/scope; an old successful operation, UI approval flag or transport possession alone is not authorization.
5. TLS and native peer pin verification, live private-key possession, installation continuity, current operation checks, durable local revoke precedence and authorization/publication fencing remain required. A valid native certificate and the selected native TLS certificate profile remain required. The historical **exact certificate-DER binding → authenticated online reissue** requirement is superseded for this local ACL; same-key renewal is not a way to bypass certificate/profile validity, pins, continuity or current ACL checks. This ADR does not define a new certificate profile or relax the frozen QR profile.

## V1 unpair

- **Online:** phone sends an authenticated request over the native peer channel. PC native durably revokes both the peer's ACL and trust, fences new operations/publication, and only then returns ACK. Phone removes its local relationship after that ACK. A lost reply is not proof of PC-confirmed revocation; completed durable final files are not automatically deleted by revoke.
- **Offline:** phone removes its local relationship immediately, truthfully reports **PC-unconfirmed**, and subsequent pairing requires fresh QR. Local removal does not claim the unreachable PC has revoked its ACL/trust. No delayed signed revoke, queued delivery or two-sided offline revocation guarantee is included in V1; those are excluded V2 possibilities, not implementation commitments.
- Online revoke endpoint/atomic ACL+trust transaction and explicit offline local-only removal are implemented; software-fixture native mTLS/HTTP and managed regression evidence is recorded below. This is not physical phone↔PC acceptance; lost ACK remains PC-unconfirmed until exact authenticated retry.

## Decisions explicitly OPEN

- Remote transport preference remains [ADR0012](0012-kloda-owned-p256-device-identity.md): WebRTC/DTLS, signed signaling/fingerprint and Kloda mutual proof, direct P2P where possible, Cloudflare TURN only as relay fallback. **FINAL remote authorization policy is OPEN.** Neither this local ACL nor the historical issuer policy is silently selected as the final remote policy.
- **Account recovery, central revocation and their relationship to an offline PC/local grants are OPEN.** This ADR chooses neither automatic survival nor automatic reset of local grants after central recovery/revocation. It does not promise immediate central revocation on an unreachable PC, nor preserve the old 24-hour promise as current local ACL policy. Account/MFA history remains history outside this scoped change.
- Native SQLite engine is now pinned through rusqlite0.39.0/default-off/bundled and libsqlite3-sys0.37.0 to SQLite3.51.3, which fixes the official WAL-reset corruption bug. Source, actual runtime WAL/FULL/reopen/BUSY/rollback smoke and existing47 native regressions were verified. Platform database protection, custody, unsupported hardware and safe-storage behavior remain OPEN; this engine update does not resolve Windows native storage or prove production ACL durability.

## Native filesystem implementation and local-writer boundary

The approved threat boundary trusts the local PC owner and local filesystem writers. Hostile remote peers and path inputs remain adversarial; V1 does **not** promise containment against a trusted local writer relocating an opened directory or introducing an outside-origin hard link into the selected tree. cap-std selected-parent/Dir-handle containment does not provide that stronger guarantee. This is an explicit threat-model boundary, not evidence that arbitrary remote paths are safe.

- The native owner has adopted cap-std4.0.3 (`default-features = false`, no optional features), with cap-primitives4.0.3. Use capability-relative operations for remote-controlled paths; hostile traversal, absolute paths and symlink escape remain denied. Never substitute string-prefix/canonicalization checks or an unconfined `std::fs` receiver fallback.
- The protected native SQLite store originally used schema3; the ADR0019 continuation adds narrow schema4 retention/deletion/admission records without changing this PC-local ACL authority. Explicit guarded Electron OS folder selection and default-Cancel per-peer consent invoke native `approveBackup`; complete PC trust alone grants no file authority. Root and per-peer directory handle identities persist; monotonic ACL revision supports current authorization. ACL-only revoke preserves trust; trust revoke atomically revokes its ACL. No media is deleted. The `backup_scope_changed` error is surfaced in the desktop UI with localized reselect/reapprove guidance; no pairing reset or media deletion is instructed.
- Historical management checkpoint: native57/policy11, desktop82/typecheck/build and four-ABI JNI/APK PASS. Current receiver checkpoint: native84/strict all-target clippy, policy15/root lint, full root suites(API1/desktop82/mobile19/sync-core117), native-Electron/main/renderer build, four-ABI JNI and Android debug APK PASS.110 Rust files/max292 nonblank. Android server-only dead-code warnings8 remain unsuppressed; build success is not physical-owner/device acceptance.
- Actual Windows identity uses volume plus 128-bit FileId via [`FILE_ID_INFO`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info) and [`GetFileInformationByHandleEx`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex); Unix uses device/inode. Unsupported identities fail closed. The Windows branch is not compiled or platform-verified here.

## Storage and transfer invariants

- ACL stays in local application data, not the selected media folder or network storage. Reuse the native serialized owner, transactions, integrity checks, bounded SQLite busy handling and close/join discipline. Capability-relative path access protects against hostile remote path traversal/symlink escape, within the approved local-writer boundary above.
- Technical failures retain completed finals and pending journal/queue: full/unplugged/unreadable media pauses work, and restart/resume revalidates current authorization before publication. Revoke stops work and cannot auto-resume; trust removal requires fresh pairing. Receiver hash verification and operation-bound durable result rules remain.
- App UI must open when ACL cannot be read, while file operations fail closed. No automatic corrupt-ACL reset, broad regrant or photo deletion. Native errors distinguish DB busy/corruption/continuity from target disk/permissions/sharing problems; UI explains cause and next action without claiming Defender or antivirus is proven from a generic access-denied code.
- The implemented management error surface distinguishes full/quota targets using stable Rust [`StorageFull`/`QuotaExceeded`](https://doc.rust-lang.org/std/io/enum.ErrorKind.html), and Windows sharing/lock failures from permanent access denial. It does not invent queue recovery or a proven Defender cause; Windows runtime and full-disk queue behavior remain unverified.
- Windows private-storage/continuity and reparse/sharing controls remain; the current storage blocker is not labelled SQLite corruption. macOS packaging/sandbox and persistent selected-folder access require actual support; Linux XDG/UID/GID and distribution sandbox rules remain gates. Physical support is not inferred from source/build.

## Consequences and evidence boundary

Native V1 implements the receiver, durable journal, completed-result query/list/restore and online unpair in [ADR0010 §6](0010-operation-bound-pc-commit-proof.md#approved-v1-sequential-contract). Actual software-fixture TCP mTLS/HTTP exercised100000-byte upload,65536-byte resume after Store reopen, finalize/reopen/list/exact restore, lost-response durable revoke/exact ACK retry and subsequent file403. Own disposable16MiB HFS+ image reached actual ENOSPC→507/backup_full; reopened offset0/hash survived and identical retry finalized/restored after removing only owned filler. Current desktop/four-ABI/APK builds passed. This is host runtime/build evidence, not production readiness, hardware custody, physical LAN or actual phone Photos sender proof. Detailed verification and limits are in [the current handoff](../implementation/implementation-session-handoff.md#v1-local-authority-adoption).
>
> Trusted local filesystem writers remain inside the approved owner boundary: remote paths stay hostile; no unconfined `std::fs` fallback or containment guarantee against local directory relocation/outside-origin hardlinks. Same-peer/same-root regrant with a new SID can read immutable completed own history only; pending work is never automatically adopted. Frozen `kloda-pair/1` is unchanged. Account recovery, central revoke, final remote authorization, Windows storage, macOS signing `-34018`/sandbox-distribution-bookmark choice, Linux physical custody/support, and actual phone Photos sender acceptance remain OPEN. No physical probes or platform gates are claimed passed.
